## 1. Measured behavior

Probe: create a job with no attempts, then a run with two attempts.

```text
empty job status: 200
empty job body: {'attempts': []}

missing job status: 404
missing job body: {'detail': 'Job not found.'}

attempt count: 2
row keys: ['attempt_no', 'candidate_sha256', 'finished_at', 'id',
           'outcome', 'reason', 'route', 'run_id', 'started_at', 'status']
attempt_no/status/route: 1 queued route_a
attempt_no/status/route: 1 queued route_b

snapshot routes A/B attempt_id: 2c03fe63… / cc7daea0…
snapshot attempt_id matches rows: True True
empty snapshot attempt_id A/B: None None
```

So the two cases are distinct and intentional:

- **no attempts on an existing job** → `200` with an empty list; the job exists,
  so there is nothing to 404;
- **job does not exist** → `404` before any attempt lookup.

## 2. Contract mapping

Record 97 (Item 1) states the client contract:

```text
GET /api/jobs/{job_id}/attempts
{"attempts": [{"id", "run_id", "route", "attempt_no", "status", "outcome",
               "reason", "candidate_sha256", "started_at", "finished_at"}]}
```

and the explicit mapping:

- `attempt_no` ← `attempts.sequence`
- `status` ← `attempts.phase`
- `reason` ← the migration-003 rename of `reason_code`
- ordering: run start, then attempt sequence (oldest first)
- `GET /api/jobs/{id}` carries `routes.A.attempt_id` / `routes.B.attempt_id`

The probe matches this mapping and the snapshot ids.
