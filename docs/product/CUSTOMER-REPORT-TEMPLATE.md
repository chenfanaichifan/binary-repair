# Customer report template

Status: prototype template (M3, 2026-11-17). It documents the customer-facing
report produced by `BT`scripts/product/export_report.py`BT` and the manual fields
an engagement owner must fill in. Generated verdicts are never edited by hand.

## 1. How the report is produced

1. Run the deterministic product demo or an engagement run:

   `BT``BT``BT`bash
   tools/product/run-demo.sh all artifacts/<engagement>/demo
   `BT``BT``BT`

2. The exporter writes:

   - `BT`REPORT.md`BT` / `BT`report.html`BT` (English, ASCII, primary);
   - `BT`REPORT.zh.md`BT` / `BT`report.zh.html`BT` (Chinese customer locale);
   - `BT`EVIDENCE-INDEX.json`BT` (SHA256 of every evidence file);
   - `BT`SHA256SUMS`BT` (full checksum list; excludes itself).

3. The engagement owner appends the manual sections described below (engagement
   scope, signatures) into a copy of the generated report. Do not edit the
   verdict, disposition, checks, candidate digest or evidence index by hand.

## 2. Report structure

| Section | Content | Source |
|---|---|---|
| 0. Product boundary | positioning, public benchmark 2/24, hidden 0/8, not-claimed | fixed text from the run boundary record |
| 1. Execution summary | fixture, expected outcome, verdict, disposition, independent verification, oracle, tier | generated |
| 2. Per-fixture results | input SHA256, scan view, repair fields, verifier checklist, limitations, not_run | generated |
| 3. Fail-closed self-check | "passed" only when no false verified claim exists | generated |
| 4. Evidence index | file, bytes, SHA256 | generated |
| 5. Not-claimed list | canonical customer wording | fixed text |
| A. Engagement scope (manual) | customer, binary identity, target sink, authorization, dates | filled by owner |
| B. Residual risk (manual) | accepted limitations, compensating controls, review owner | filled by owner |
| C. Sign-off (manual) | who reviewed, role separation statement | filled by owner |

## 3. Manual engagement block (copy into the report)

`BT``BT``BT`markdown
## A. Engagement scope

- Customer: <CUSTOMER>
- Engagement id: <ID>
- Binary: <FILE NAME> (SHA256 <SHA256>)
- Target function / sink: <SYMBOL OR VA RANGE>
- Vulnerability class / reference: <CWE / CVE / advisory>
- PoC manifest: <PATH OR "none">
- Regression cases: <COUNT OR "none">
- Authorization: <WRITTEN AUTHORIZATION REFERENCE>
- Operator: <NAME>; review: <NAME>; date: <YYYY-MM-DD>

## B. Residual risk

- Scope of evidence: one target function plus the supplied PoC/regression cases;
  this is not a whole-program proof.
- Accepted limitations: <LIST FROM THE GENERATED REPORT>
- Compensating controls: <DEPLOYMENT/REVIEW/ROLLBACK CONTROLS>
- Residual risk owner: <NAME>

## C. Sign-off

- Verification row signed by: <NAME> (role)
- Approval row signed by: <NAME> (role)
- Independence statement: see LIMITATIONS section 4 - in this delivery the
  verification and approval rows were signed by the same operator
  (role-separated, not independent two-person review). A customer that requires
  truly independent approval must add its own reviewer.
`BT``BT``BT`

## 4. Rules for writing a customer report

1. If the disposition is not `BT`verified_patch`BT`, section 2 must say that no
   candidate bytes are delivered and why (refused / rejected / not verified);
2. Never move a limitation out of the report, never delete a not_run row;
3. Always quote the canonical numbers: public benchmark 2/24 verified (8.3%),
   hidden 0/8;
4. Never claim "arbitrary binary", "100%", "universal", "production safe";
5. The evidence index is authoritative: any file not in `BT`SHA256SUMS`BT` is not
   part of the delivery;
6. Customer binaries and credentials are never placed in the report; only the
   digest and the declared target are recorded;
7. Reports are retained only as long as the engagement requires; see
   `BT`DEPLOYMENT-AND-PACKAGING.md`BT` for data handling.

## 5. Pre-send checklist

- [ ] Generated by the scripts, not hand-written verdicts;
- [ ] Fail-closed self-check reads "passed";
- [ ] `BT`shasum -a 256 -c SHA256SUMS`BT` passes in the delivery directory;
- [ ] Manual sections A/B/C are filled and the authorization reference is present;
- [ ] The 2/24 and 0/8 numbers are present;
- [ ] No API keys, internal paths or customer secrets in the document;
- [ ] The report is delivered with the evidence package described in
      `BT`DELIVERY-PACKAGE.md`BT`.
