# 二进制溢出的“表面证据”与下一步

## 已实现

`scripts/binary_overflow_surface.py` 对本地二进制做只读检查：

- `nm -u`：提取未解析/导入符号，标记 `strcpy`、`strcat`、`sprintf`、`gets`、`memcpy`、`printf`、`malloc`、`read`、`recv` 等溢出相关 API；
- `strings`：提取可能包含 `%s`/`%n` 的格式化字符串；
- 记录 SHA-256、限制和“不是漏洞结论”声明。

`knowledge/overflow_validation.json` 还对 12 个种子在 `clang -O0` 下编译，记录原始/补丁的导入面。

## 为什么这还不够

导入 `memcpy` 不等于存在溢出：容量、索引、长度来源、路径可达性都在调用点。反过来，优化/内联/静态链接也可能让危险 API 消失。

因此完整链路必须是：

```text
导入/字符串表面
  -> 反汇编/IR（Ghidra、objdump、angr）
  -> 栈帧/堆分配/容量/长度来源（DWARF、数据流）
  -> 路径约束（符号执行）
  -> 动态 ASan/UBSan + fuzz
  -> 差分/等价验证
```

## 对模型训练的含义

仅用“二进制里是否出现 strcpy”做标签，会把大量安全调用误标为漏洞。更可靠的标签必须包含：

- CWE / 具体根因；
- 触发输入约束；
- 容量与长度来源；
- 修复前后差分；
- 编译器/架构/优化级别；
- 证据等级（是否实际触发、是否验证）。

这也是当前知识库明确区分 **规则命中、候选分类、编译通过、动态验证** 的原因。
