`docs/status/claims.json` (`non_goals`) and to the enforcement that keeps it from
being reported as a success. It is also the human-readable roadmap of record for
the 12 accepted non-goal ids. The source of truth is the measured audit:
`artifacts/capability-gap-audit-2026-11-14/coverage-matrix.json`
(`gap-report.md` is the human view). Rows are re-measured by
`scripts/audit_capability_coverage.py`; this page is the mapping/registry and the
roadmap, not a second status list.

dynamic_unverified 0, mitigated 1, closed 55, **non_goal 12**), capability
universe **unknown 0**. The 12 non-goal ids below are the complete mapped set:
they match the measured audit rows and `docs/status/claims.json` `non_goals`

## 1. Enforcement vocabulary (what the product does for that class, never a success)

- `unsupported` - the input/strategy returns `unsupported`; no candidate bytes.
- `analysis_only` - analysed, no patchable sink for the declared target; no candidate.
- `not_run` / `no verified` - runtime evidence is missing; the gate stays
  `not_run`/`inconclusive`; `verified_patch` and download are never produced.
- `no download` - even a static-only opt-in candidate is explicitly unverified.

## 3. Roadmap management (same 12 ids)

This is the productization roadmap for the same 12 mapped ids. The four fields
are the roadmap contract: `roadmap_stage` says what is planned, `owning_area`
names the accountable engineering area, `research_acceptance` states the
evidence that would move the id to supported, and `quarterly_review` is the next
scheduled review date (never later than the row's `review_by`). The
machine-readable mirror of this table is the `non_goals` list in
`docs/status/claims.json`; the same 12 ids and the four field values are mirrored
verbatim and are updated by the release owner together with this page, so the two
must agree at every quarterly review and release.

`roadmap_stage` vocabulary (closed set):

- `keep-non-goal` - accepted as out of product scope; no productization work is
  planned, but the quarterly review may re-open it with evidence.
- `research` - the evidence/feasibility does not exist yet; research work is
  required before a productization decision.
- `productize-next` - concrete engineering evidence exists or is planned for the
  next productization cycle; the graduation path in section 4.2 is the checklist.
- `runtime-fallback` - limited by a measured platform/runtime capability; the
  product falls back to `unsupported`/`not_run` with the probe reason and never
  fakes the missing capability.

`owning_area` vocabulary (closed set): `solver` (analyzer, deterministic
templates, repair engine), `runtime` (guest runners, capability probes,

## 4. Governance: quarterly review, graduation and fail-closed rules

### 4.1 Quarterly review procedure

1. Cadence: every quarter on 2027-02-14, 2027-05-14, 2027-08-14 and
   2027-11-14; the next scheduled review for this snapshot is **2027-02-14**
   (the `quarterly_review` column above). A review can be held earlier, never
   later than the row's `review_by`.
2. Re-measure before deciding: the audit owner re-runs
   `scripts/audit_capability_coverage.py` and the local coverage gate
   (`scripts/verify_coverage_gate.py --local`, or the release gate). The measured
   `non_goal` id set must equal this page's 12 ids and `claims.json`
   `non_goals`; a mismatch blocks release and is reported as a mismatch - this
   page and `claims.json` are never edited to hide it.
3. Owner evidence: for each id the `owning_area` presents evidence against
   `research_acceptance` (or an explicit "no new evidence" statement). The review
   then does exactly one of: re-affirm the current `roadmap_stage`; advance the
   stage; mark it `runtime-fallback` permanent with the measured capability
   reason; or graduate it through section 4.2.
4. Dates: every review sets the next `quarterly_review` date. No `review_by`
   may be later than 2027-05-14, and a `review_by` that passes without a recorded
   decision is a release blocker. Extending a `review_by` requires the same
   owner evidence review as graduating it.
5. Record: the release owner updates `claims.json` (machine-readable mirror) and
   this page in the same change, then runs the coverage gate so the measured
   audit, the claims ids and this page agree. Roadmap metadata never overrides
   measured status.

### 4.2 Graduation path (all five steps required, in order)

An id only moves from non-goal to supported when **all** of the following exist
and are evidence-linked from this page:

1. **Fixture** - a checked-in deterministic fixture (original bytes, expected
   behaviour and, where applicable, the PoC/regression input) that exercises the
   exact family and can fail/pass deterministically.
2. **Runtime oracle** - measured execution evidence for that fixture
   (native/emulated/guest/PoC as appropriate). The runtime-capability probe must
   report the required tier available with an explicit reason; if the oracle is
   unavailable the id stays non-goal/runtime-fallback and is never faked.
3. **Evidence profile** - the declared acceptance evidence model in
   `app/services/repair_matrix.py` is extended (evidence sources and required
   checks) for the new capability; oracles are not mixed (the stack/emulated
   oracle never verifies non-stack destinations; non-stack and PoC-requiring
   repairs use the external-PoC profile).
4. **Gate check** - the unified verification gate emits and enforces the
   declared required check; a tampered, absent or mismatched evidence packet
   stays rejected/inconclusive. The legacy stack/emulated gate keeps its
   fail-closed `manifest.legacy_gate_unsupported` behaviour and is never the
   gate for manifest-bearing requests.
5. **Claims and measurement** - only after steps 1-4 pass, the release owner
   moves the id out of `claims.json` `non_goals` (or marks it supported), the
   audit re-measures the id as supported/closed, this page moves the row from
   this registry into the supported-capability inventory with evidence links, and
   the coverage gate accepts the measured state. Documentation alone never
   graduates an id.

### 4.3 Fail-closed rules for detected non-goal inputs

These rules are release blockers, not documentation preferences. A detected
non-goal input must **never** produce `verified_patch` or a download:

1. The declared enforcement for each row is mandatory: `unsupported` ->
   `unsupported` outcome and no candidate; `analysis_only` -> no candidate and
   no download; `not_run`/`inconclusive` -> no success, no evidence hash and no
   download; `no verified` -> `verified_patch` is never emitted.
2. A non-goal input that hits a missing runtime/oracle must become
   `not_run`/`inconclusive`, never a fabricated pass and never a repair failure
   that hides the gap.
3. No download path exists unless the deterministic gate returned
   `success_within_scope` with every required check passed and a complete
   evidence hash. A static-only opt-in candidate stays explicitly unverified and
   is never counted as success.
4. Manifest-bearing requests never use the legacy stack/emulated gate
   (`manifest.legacy_gate_unsupported` is a required failed check if it is ever
   supplied there); manifest evidence routes only to the unified
   evidence-profile gate.
5. The safe default policy stays in force: no declared target and no explicit
   whole-image opt-in means `analysis_only`; a verified candidate requires the
   declared target scope and a passed patch-ownership check.
6. The acceptance-invariant engine (`app/services/acceptance_invariants.py`)
   checks these properties on committed packets in the release gate; an
   invariant violation fails the release. Editing this page, `claims.json` or the
   report cannot change gateway behaviour - behaviour changes only through
   measured code, fixtures and gate evidence.

## 6. What the coverage gate enforces

`scripts/verify_coverage_gate.py` (default `--static-only`, CI/PR mode) asserts:

1. no `GM-detector-error::*` audit rows (the audit itself must be healthy);
2. no high-severity open gaps;
3. open gap ids are a subset of the explicit `ALLOWED_OPEN` residual set
   documented in the script header (currently empty, no silent acceptance);
4. every measured `non_goal` gap id is mapped in this page or in
   `docs/status/claims.json` `non_goals`; every claims non-goal id is measured
   as a static `non_goal` or `dynamic_unverified` audit row;
5. `docs/status/claims.json` `non_goals` entries are structurally valid:
   `id`/`category`/`enforcement`/`claim`/`owner`/`review_by` (ISO date,
   <= 2027-05-14)/`productization_criteria`/`fallback`, all 12 present;
6. probe-dependent gaps are honest in static mode: they are
   `dynamic_unverified` (neither closed/mitigated nor open) and counted; the
   capability universe has `unknown == 0`, every non_goal/unavailable cell has
   an explicit reason, non_goal cells referencing claims ids are mapped, the
   status counts agree with the cells, and every declared dimension value
   appears in at least one cell;
7. the meta-audit passes (detector recall >= 0.8, precision = 1.0, injected
   defects detected, fabricated gaps rejected) - exposed in static mode,
   required in `--local`;
8. the acceptance-invariant engine accepts the committed acceptance evidence
   (`verified`/`rejected`/`not_run`/target-scope/rewrite/manifest-legacy/
   download invariants) - exposed in static mode, required in `--local`.

`--local` additionally runs the bounded dynamic audit probes and requires the
real-guest acceptance capture `artifacts/coverage-closure-2026-11-14/
acceptance.json` to exist with `passed: true`, `dynamic_unverified_count == 0`,
the claims ids to equal the measured `non_goal` ids exactly, the meta-audit to
pass and the invariant engine to pass over the committed packets.

Status is measured, never hard-coded: a detector closes a row only from live
imports/probes, and this page/claims list is regenerated from the measured
audit ids by the audit owner.
