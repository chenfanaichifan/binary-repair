## 2. Hypothesis framework

For each disagreement three families are considered:

* **A - candidate defect**: the generated bytes are wrong or do not implement
  the claimed repair. Evidence that would support A: independent oracle failure
  on candidate bytes, identity/hash mismatch, container corruption, the guard or
  capacity rewrite not present at the claimed site.
* **B - verifier semantics/evidence-exchange gap**: the candidate may be
  admissible, but the verifier cannot express or receive the facts needed to
  check it (resolved scope, resized-candidate replay, associated changes, ABI
  evidence, patch plan, oracle runner).
* **C - scope/contract/oracle wiring**: the pipeline and verifier disagree about
  what "the target" or "the evidence" is (scope contract, oracle exchange,
  runner artifact exchange), independent of candidate correctness.

No generator claim is copied as candidate correctness. The phrase "not verified"
below means the independent verifier did not accept the candidate; it does not
mean the candidate was proven wrong.

## 4. Independent adjudication experiments

Each sample packet records the verifier reports and experiments E0-E4:

* **E0**: module API without `run_poc` - reproduces the CLI decision and
  `runtime-oracle=not_run`.
* **E1**: module API with the real `run_poc` - oracle executes and passes for
  both samples; the remaining failures are therefore not oracle-availability
  failures.
* **E2**: exchange the pipeline-resolved target scope (va/end) - stack
  `target-scope` flips from `not_run` to `passed`; heap `target-scope` remains
  `failed` because the associated .rodata action is outside the declared range.
* **E3**: derive an ABI block from the resolved code range and feed it in - the
  ABI check becomes runnable (status recorded in the artifact). For the stack
  sample a function-sized derived block passes (`block 174772+44`); for the
  capacity sample a naively derived 16-byte site block fails ABI
  (`branch_target_unknown`, `no_ret`), which shows the derivation must use the
  real function/ABI region, not the rewrite site. In both cases the gap is that
  the producer/runner never derive or exchange the block.
* **E4**: associated-change modeling - the verifier recomputes raw byte diffs;
  metadata/contract has no associated-change field, so the `.rodata` action is
  rejected by target scope even though the pipeline gate never saw it in
  `actions`.

## 5. Conclusions

* **Stack guard candidate (candidate issue: none observed).** The candidate is
  resized by cave injection and the pipeline PoC oracle passes; the independent
  oracle passes when actually executed (E1). The verifier rejects it because
  (a) the resolved scope is not exchanged, (b) the resized candidate cannot be
  replayed by the rewrite-only `action-replay` model, (c) no ABI evidence is
  exchanged, and (d) no patch-plan contract exists to declare insertion/cave
  semantics. This is primarily a **verifier/evidence-exchange gap (B/C)**, not
  a demonstrated candidate defect. The candidate is **not verified** and remains
  unaccepted until a resized-candidate replay contract exists.
* **Heap capacity candidate (candidate issue: none observed).** This is
  primarily an **evidence-exchange gap (C)**: the engine's `.rodata` message
  alignment is an associated change outside `report.actions`, the pipeline gate
  checks only `actions`, and the verifier recomputes the raw diff and applies
  target scope to all diffs without any associated-change channel. The
  candidate is not resized (V8B-03 does not apply) and the independent oracle
  passes when injected; ABI/plan exchange gaps remain. The candidate is **not
  verified**.
* No rule may be loosened just to make a candidate pass. The B2 implementation
  must add explicit contracts (patch plan, associated changes, resolved scope,
  ABI evidence, oracle execution) and verify them fail-closed; undeclared
  out-of-scope changes must continue to be rejected.

## 6. Status of this baseline

Both disagreements reproduce deterministically with candidate hashes matching
the Phase-8A benchmark. The candidate bytes are committed as **evidence-only**
artifacts (see the per-sample `metadata.json` and README): they are not executed
outside the sandbox and are not a correctness or verified claim. Dynamic oracle
status is host-dependent and recorded truthfully (`pass` here; `not_run` would be
recorded instead of a fabricated pass). Production code, contracts, CI, claims,
benchmark v1 and the release gate were not modified.
