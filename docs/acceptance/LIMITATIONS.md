# Limitations of this delivery

This repository is an accepted MVP **with recorded limitations**. Do not cite it
as a fully independent, binary-level-proven, universally green product.

## 1. V4 is model-level

V4 is a typed symbolic claim over the target function. It is not binary-level
symbolic execution and not a whole-program proof. The result is `passed` at
`scope=model`; the binary-level claim is not made.

## 2. Coverage is a bounded fixture/matrix, not arbitrary binaries

The historical V4 delivery covered the public CWE-416 no-input path and the
CWE-121 MVP fixture.  v5/v6 add a deterministic matrix over 13 synthetic
fixtures (ELF/PE/Mach-O x86-64/arm64, ELF32/PE32 i386) and two AI direct-binary
protocols, but this is still not evidence that arbitrary binaries, other
architectures, other compilers, stripped production binaries, or client binaries
work.  See section 9 for the exact matrix/sink boundary.

## 3. Test environment

Current acceptance is the non-browser suite:

```text
macOS 13.5 arm64: 1143 tests, 0 failed, 0 errors, 7 skipped (264.0 s)
Linux VM Ubuntu 24.04 arm64: 1143 tests, 0 failed, 0 errors, 10 skipped (264.1 s)
GitHub Actions Ubuntu 24.04: workflow success on the final commits
```

The platform-gated skips are recorded in the acceptance files (Mach-O native
cases on Linux; Linux execution cases on macOS).  E2E/browser tests remain a
separate command and are not part of these counts.  Windows hosts are not the
acceptance record.

## 4. M4 verifier and Lead approver are the same operator

The verification row and approval row were signed by the same operator. This is
**role-separated, not independent two-person review**. A client requiring
genuinely independent approval is not satisfied by this delivery.

## 5. Review 9–12 original text is not recovered

The verdict is against a canonical reconstruction. It must not be described as
verbatim original review text. The source state is recorded in
`docs/development/reviews/review-9-12-m4-verdict-2026-11-07.json`.

## 6. V5 scope

V5 is build/replay reproducibility. It does not prove repaired behaviour.
`V5-replay.json` is a reproducibility result, and the four original logs are
tracked as evidence; they are not regenerated by this snapshot.

## 7. No tag or original-main merge

This repository is a curated delivery snapshot. It is not a release tag and is
not merged into the original repository's `main`.

## 8. Not a production product

This is a course/MVP deliverable, not a supported commercial vulnerability
remediation service. No client binaries, credentials, private keys or private
logs are included.

## 9. v5 "arbitrary binary" scope

v5 adds a universal binary-repair entry (`/binary`, CLI, `/api/binary/*`) and
explicit dispositions, but it is still not universal vulnerability repair:

- the deterministic repair matrix is ELF/PE/Mach-O on x86-64/arm64 plus 32-bit
  x86 (ELF32/PE32). Only copy sinks with a recoverable capacity are repaired
  (`strcpy`/`strcat`/`stpcpy` guards; constant-length `memcpy`/`memmove`/syscall
  clamps). Heap/global destinations, `sprintf` format expansion, UAF, integer
  and loop defects, and obfuscated/inlined copies are **analysis-only**;
- 32-bit x86 analysis models **push-materialised cdecl arguments**; argument
  setup such as `mov [esp+K], reg` is not analysed in v1 (fail-closed, keeps the
  i386 negative control honest); static-libc alias names not ending in a plain
  copy alias (for example `compiler_rt.memcpy.memcpyFast`) are also fail-closed;
- a candidate repairs **one function per run**; other vulnerable functions found
  in the image are reported as limitations and not patched, so every shipped
  action stays covered by the runtime case for that function;
- 32-bit Mach-O, fat Mach-O rewriting, arm32, riscv, mips, powerpc and
  big-endian containers are detected and analysed but never rewritten; fat
  Mach-O slices are reported individually (`slices[]`) but no fat binary is
  rebuilt;
- capacity is frame geometry (`frame_top - destination`) or an explicit
  `_chk`/immediate size, not DWARF object size; buffers that do not sit at the
  frame top can be over-estimated;
- PE and ELF runtime evidence is Unicorn instruction-level emulation of the
  repaired function, not a Windows/Linux kernel run. Mach-O native evidence
  exists only on macOS; elsewhere those candidates are `not_verified`;
- `static_only_patch` is explicit opt-in, unverified, and never reported as
  success. A failed gate drops the candidate (`rejected`); matrix-outside input
  returns `unsupported`/`analysis_only` and no bytes;
- report v4 dispositions are bounded claims: no whole-program proof, no
  arbitrary-vulnerability discovery, no claim that a repaired binary is safe for
  production use. See
  [`docs/acceptance/binary-universal-v5-2026-11-13.md`](binary-universal-v5-2026-11-13.md).

## 10. readelf dependency (Route B static audit)

`tests/test_routeb_executor.py` requires either all five independent views
(`readelf` + `objdump`) or none; a host with `objdump` but no GNU `readelf`
produces one view and fails the view-count assertion.  The earlier macOS failure
was fixed by installing Homebrew GNU readelf 2.47, **not** by replacing the
backend or weakening the test.  Stock macOS without GNU readelf can reproduce
it; Ubuntu CI installs binutils.  Historical failing JUnit is preserved in
`artifacts/binary-universal-2026-11-13/junit.xml`.


When original runtime evidence exists, the unified gate requires
`poc.original_fails` / `poc.candidate_passes` on the same capacity/input probe;
this is a function-level runtime differential, not a full guest/kernel PoC
replay.  Full native/guest PoC replay with per-fixture manifests and regression
suites remains future work for every path.

## 12. AI increment is not measured

The two AI direct-binary paths prove protocol/validator/writeback/gate
integration with a scripted client.  The scripted model instantiates the same
deterministic actions, so candidates coincide with the v5 baseline and no AI
increment is measured.  Real-LLM quality, a gate-blind increment suite and
PoC-based evaluation remain future work; AI never owns acceptance.

## AI binary-repair paths (v6)

- Exactly two product paths: `asm_roundtrip` (ELF i386/x86_64/arm64; requires
  host `clang`; assembly text is intentionally used) and `binary_direct`
  (ELF/PE/Mach-O x86_64/arm64 and ELF32/PE32 i386; no assembly text).
- Neither path decompiles to C and recompiles.  `ai_plan`/`ai_bytes` are
  internal prototype names only, not API/UI paths.
- One sink/target function per AI candidate; multi-function model selection is
  not implemented.
- `binary_direct` validates structure (complete Capstone decode, instruction
  allowlist, injection/redirect ranges, same-length executable edits, container
  reparse); semantic correctness is still decided by the deterministic runtime
  gate.  A structurally valid but semantically wrong block can be rejected by
  the gate, never promoted by the model.
- `asm_roundtrip` also validates assembled machine code with the same kind of
  allowlist and the shim only redirects the analysed function entry; it requires
  clang and an ELF target.
- Mach-O direct-path positive evidence exists only on macOS (native gate); on
  Linux those tests/evidence entries are platform-skipped.
- When the original runtime is available, a PoC-style differential
  (original fails / candidate passes) is now a required gate predicate; it is a
  function-level runtime differential, not a full guest/kernel PoC replay.
- Gate blind-spot experiment: 4/5 semantically deviant scripted candidates are
  caught; one residual blind spot remains (stdout/`puts` side effects are not
  compared by the runtime oracle).  See
  `artifacts/gate-blind-spots-2026-11-13/`.
- Real-provider experiment (six tasks) measured **3/6 AI verified vs 6/6
  deterministic baseline, 0 coverage increments**; see
  `artifacts/ai-real-provider-2026-11-13/`.  Real-LLM quality is not a CI
  guarantee, and no AI increment is demonstrated on cases the baseline already
  repairs.


## 12. Native PoC manifest gate

When a PoC manifest is supplied (`fixtures/poc/*.json`, API multipart field
`poc_manifest`, CLI `--poc`), the candidate is executed against the original
and candidate binaries in a temporary directory with a scrubbed environment and
timeout.  The gate requires the original to fail the PoC, the candidate to pass,
and regression outputs to match.  On macOS, ELF x86-64 PoC execution needs
qemu-user; without it the result is `unavailable` and never verified.  PE and
32-bit Mach-O PoC execution remain unavailable.  Native execution is only
enabled for trusted fixtures/CI in this delivery; executing arbitrary uploaded
binaries natively is not a security boundary.


## 13. Hard-case benchmark is initial

The hard-case benchmark was expanded from the initial two cases to 10 cases
(six inline-loop variants plus CWE121/multicall/sprintf/nonconst), with two
additional non-loop probes (UAF, heap-canary).  Success remains limited to the
inline-loop family: 6/10 primary cases, 0/2 diversity probes.  This is evidence,
not a general AI-increment claim; the benchmark and paradigm A remain future
work.


## 14. Fairness ablation is small and single-model

The 10-case fairness ablation shows target-localized AI 6/10 vs target-aware
deterministic 0/10 and blind AI 0/10, with no measured contract-specificity
effect.  It is one provider/model, 10 non-independent cases, and seven repeated
runs; it is not a population estimate.  Target/PoC/contract is still benchmark
tooling, not a product API; the puts side-effect blind spot remains.


## 15. UAF and heap diversity probes are not successes

The UAF no-input probe is supported as a real native PoC case (exact stdout hex,
no regression inputs), but the deterministic baseline is `analysis_only` and
target-localized AI produced no candidate because external calls are forbidden
in the leaf-only assembly path.  UAF and heap-canary are recorded as 0/1 each; they do not
broaden the six-loop family success.  Heap silent overflow without a guard
still needs an allocator canary oracle.
