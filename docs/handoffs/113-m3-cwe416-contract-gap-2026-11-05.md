## 3. What the CWE416 original actually does

| Quantity | Value | Source |
|---|---|---|
| exit code | 0 | `trigger-observation.txt` §1 |
| stdout | `05 04 0a` — 3 bytes | same |
| stderr | empty | same |
| determinism | 50/50 identical under `setarch -R` | §2 |
| with ASLR on | 10 runs, 10 distinct stdout values | §3 |
| correct behaviour | 99 × `A` + `\n` = 100 bytes, exit 0 | §4 |

The defect is **silent**: exit status and stderr are exactly what a correct
program produces. Only the stdout bytes differ. That is a useful property for a
trigger and a hostile property for a test matrix, which is where §4 runs into
trouble.

## 4. Why 4 + 2 cannot be written for this fixture

The CWE121 manifest works because each case is a **different execution**: four
valid inputs and two invalid inputs, each with a full expected
`(return_code, stdout, stderr, allowed_output_files)` tuple. The matrix samples
the input domain.

CWE416 `_01` has **no input**. `harness.c` takes `void`, `bad()` mallocs, fills,
frees and reads. There is exactly one execution path, so there are exactly two
distinct full expectations:

| Expectation | return_code | stdout | stderr |
|---|---|---|---|
| as-built (defect present) | 0 | `05 04 0a` (3 B) | `""` |
| repaired (defect removed) | 0 | 99 × `A` + `\n` (100 B) | `""` |

A manifest case must assert a **whole** tuple; it cannot assert "exit code only"
or "stdout ends with a newline". So the reachable matrix is **2 cases, not 6**,
and those two are *before / after*, not *valid / invalid*.

Filling the gap with assertion slices does not work either, for a reason worth
recording: the four "valid" slices I would want (exit 0, empty stderr, newline
terminated, no output files) cannot be expressed, because each case still has to
commit to a `stdout` value — and the as-built stdout differs from the repaired
one. Writing `05040a` into a `valid` case would encode the defect as required
behaviour and fail the repaired binary. Writing the repaired bytes into a `valid`
case would fail the original, which contradicts `valid` meaning "preserved".

The judging layer enforces the input-boundary reading directly:

```
tests/v3_oracle.py:199   if kind == "invalid" and length <= max_valid_len:
tests/v3_oracle.py:200       raise ManifestError(... "must exceed max_valid_len")
```

`_payload_len` returns 0 when `argv` has no second element (`v3_oracle.py:171-173`),
so every CWE416 case has payload 0 and **every `invalid` case is rejected before a
candidate is ever judged**. The manifest cannot even load.

This is not a wording problem I can solve by relabelling. The layer is built on
"invalid means an input longer than the buffer".

## 5. Why no contract can be written either

`SecurityContract` (`app/domain/contracts.py:124-197`) requires twelve fields and
validates them as numbers and byte-strings. Nine of them map onto CWE416
honestly; four do not:

| Field | CWE121 meaning | CWE416 reality | Honest fill? |
|---|---|---|---|
| `target_entry` | the sink | `CWE416_…_char_01_bad` | **yes** |
| `target_signature` | `void badSink(char *data)` | `void …_bad(void)` | **yes** |
| `dest_capacity_bytes` | `char dest[50]` | `malloc(100*sizeof(char))` | **yes** — 100 |
| `max_valid_input_bytes` | 49 | `memset(…, 100-1)` then `data[99]='\0'` | **yes** — 99 |
| `capacity_includes_terminator` | `true` | `true` (`data[99]='\0'`) | **yes** |
| `valid_domain` | input length 0..49 | text field; describable | **yes** |
| `valid_behavior` | strcpy + printLine | printLine of the allocated string | **yes** |
| `forbidden_behavior` | write past dest[50] | read after `free(data)` | **yes** |
| `invalid_input_response` | print stderr, exit 1 | **no invalid input exists** | **no** |
| `invalid_exit_code` | 1 | **there is no rejection path** | **no** |
| `invalid_stdout` | `""` | — | **no** |
| `invalid_stderr` | `"ERROR: …"` | — | **no** |

Those four fields are not optional and not nullable. Worse, they are *used*:

```
routea/cave.py:167      if not contract.invalid_stderr:
routea/cave.py:168          raise RouteAError("contract has no invalid_stderr")
routea/cave.py:169      message = contract.invalid_stderr.encode("ascii")

routea/worker.py:316-320    same check, plus a 512-byte limit
```

Route A's patch generator reads `invalid_stderr` and **writes that message into
the repaired binary**. That is the correct shape for an input-validation repair:
add a bound check, print a diagnostic, exit. It is the wrong shape for a
use-after-free, whose correct repair emits nothing and changes no exit status.

So the options for those four fields are:

1. fill a message — the tool then injects a diagnostic into a program that should
   print `A`s, i.e. it builds the wrong repair and calls it correct;
2. fill `""` — `cave.py` refuses before building anything.

There is no third option inside schema v2.

### The shape, stated once

| | CWE121 | CWE416 |
|---|---|---|
| Defect | missing bound check | use after `free` |
| Trigger | input length ≥ 50 | no input; unconditional |
| Correct repair | reject the input, exit non-zero | stop using the freed pointer; still exit 0 |
| Observable after repair | new stderr line, new exit code | **only** stdout content changes back to the allocated string |
| Contract shape | input-validation | lifetime |

Every layer assumes the left column: `SecurityContract`'s `invalid_*` quartet,
`routea/cave.py`'s injected message, and `v3_oracle`'s "invalid must exceed
`max_valid_len`". CWE416 is the right column all the way down.

## 6. Three ways forward, with the cost of each

**A. Extend the contract and Route A for lifetime repairs.** Needs, at minimum, a
`repair_kind` discriminator on `SecurityContract` (`reject_invalid_input` |
`remove_defect`), `invalid_*` becoming conditional, a non-message patch form in
`routea/cave.py` and `routea/worker.py`, and an `input_model: "none"` branch in
`v3_oracle` that judges full-tuple cases instead of argv lengths. That is M5's
schema and Route A's generator — **not my write range**, and I have not written
any of it. Estimated landing cost is a revision bump plus a re-review of every
existing contract, because `CONTRACT_SCHEMA_VERSION` is checked exactly
(`contracts.py:146-147`).

**B. Keep CWE416 and accept a 2-case matrix.** Usable as a *trigger* and as a
before/after demonstration, which is what T30 already is. It cannot carry a
`valid`/`invalid` matrix, so it cannot satisfy the obligation that asks for one.
This is the cheapest honest option and it does not unblock T8.3.

**C. Pick an input-boundary defect as the second class.** CWE122 (heap buffer
overflow), CWE124 (buffer underwrite), CWE126 (buffer over-read) and CWE127
(under-read) all keep the left-column shape: an input length crosses a bound, the
repair rejects it, and the contract, the patch generator and the oracle already
express it. They are genuinely different CWE classes from 121, so they satisfy
"second defect class" without inventing anything.

Availability is checked, not assumed: the archive holds **118 CWE families**, and
all four of these are present —
`CWE122_Heap_Based_Buffer_Overflow`, `CWE124_Buffer_Underwrite`,
`CWE126_Buffer_Overread`, `CWE127_Buffer_Underread`. No new provenance chain is
needed; they come from the same 152,957,342 B download whose SHA-256 already
matches `provenance.md`.

Cost: choose a member, build it in the guest, measure the boundary. T30's work is
not wasted — it proves the team can build and pin a second Juliet fixture from a
hash-pinned source, which is the hard half.

My recommendation is **C for T8.3**, with T30 kept as the trigger-capability
record. I am not making that call; it belongs to the Lead, and it changes the
defect class the task named.

If C is chosen, note the Juliet 1.3 archive contains the whole suite, so the case
files are all reachable from the same 152,957,342 B download whose SHA-256 is
recorded in `provenance.md` — no new provenance chain is needed.
