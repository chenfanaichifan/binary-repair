## What this establishes

1. The shipped wrapper supports exactly three modes: `gate3`, `probe`, `gate4`.
   There is no `gate5`, so D3's intended invocation
   `jobwrap gate5 -- <repo>/routeb/jobwrap_gate5.sh <repo> <work-dir>`
   terminates at `jobwrap: unsupported mode` before any script runs.
2. The binary names its own source as `jobwrap_v3.c`. That source is not in this
   checkout, so a `gate5` mode cannot be built here without it.
3. `routeb/jobwrap_gate5.sh` **does** exist at integration head `aab162a` and
   already takes fixed argv (`<repo> <work-dir>`) and reads `GATE5_SCRIPT` from
   the environment. So the shell half of D3 is delivered.
4. That shell half is still incomplete against D3: it accepts **any** executable
   path in `GATE5_SCRIPT` and never hashes it. D3 asked for the caller-supplied
   script to be hash-checked, and it is not.

## What would unblock Gate 5

Two changes, neither of which is a Gate 5 pass:

1. a `jobwrap` build with a `gate5` mode that runs one fixed script path with
   fixed argv (requires `jobwrap_v3.c` or its successor);
2. `GATE5_SCRIPT_SHA256` accepted by `jobwrap_gate5.sh` and verified before
   `exec`, failing closed when the variable is missing.

Until both exist, Gate 5 stays BLOCKED and the MVP cannot claim it. No host-side
run was attempted and no Gate 5 result was substituted for Gate 4.
