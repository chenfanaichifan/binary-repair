## Problem

T6.0 recorded the worker's executor contract as eight `BINARYREPAIR_*` variables.
The Route B adapter that consumes them (`app/services/attempt_writer.py
--routeb-bundle`) needs the **static bundle directory**, and nothing in the host
supplied that path. `routeb/attempt_writer.py --from-env` additionally hard-fails
with `BINARYREPAIR_ROUTEB_BUNDLE is required`. In practice every Route B attempt
started with a valid environment would have died as `error / tool_failed`, and the
message would not have said why (the worker did not capture executor stderr).

## What changed

### `app/services/attempt_driver.py` (new)

One entry point for `BINARYREPAIR_ATTEMPT_CMD`:

```
python -m app.services.attempt_driver
```

It validates the worker environment, resolves the Route B evidence directory, and
delegates to `app.services.attempt_writer`. It never executes, loads, or links the
candidate or the original, and it never invents a gate value — an absent check
stays `not_run`.

Route B evidence resolution order:

1. `BINARYREPAIR_ROUTEB_BUNDLE` when set (explicit override);
2. otherwise the canonical path derived from the attempt:
   `<data>/jobs/<job>/runs/<run>/attempts/<attempt>.routeb`.

The guest writes that directory; the host only reads it.

Exit codes (documented in the module and stable for wrappers):

| Code | Meaning |
|---|---|
| `0` | Worker result bundle written at `BINARYREPAIR_RESULT_PATH` |
| `2` | Incomplete worker environment, or unknown route |
| `3` | Route B evidence directory missing / no `candidate.elf` |
| `4` | `route_a` has no adapter input (`BINARYREPAIR_ATTEMPT_INPUT`) yet |

Every non-zero path leaves **no** result bundle, so the worker cannot mistake a
missing evidence directory for a measured outcome.

### `app/services/worker.py`

- Injects a ninth variable, `BINARYREPAIR_ROUTEB_BUNDLE`, always set to the
  canonical staging path. The path is derived from ids the worker already has, so
  a wrapper needs no extra configuration and two runs of the same attempt agree.
- `BINARYREPAIR_ATTEMPT_CMD` now accepts a command line, not only a single
  executable path: a value naming an existing file runs as-is (preserving the old
  contract for wrappers whose path contains spaces), otherwise it is split with
  `shlex.split`. This is what lets `python -m app.services.attempt_driver` be the
  command.
- Executor failures capture stderr and surface its last line in the attempt
  detail, so `error / tool_failed` now says *why* (for example
  `route_b evidence directory is missing: ...`). Previously the reason went only
  to the console.

### `Improve.md` item 6 (configuration split)

`start-controller.ps1` defaulted to `var\controller` while `start-worker.ps1`
defaulted to `var`. Two terminals following the documented commands read
different SQLite stores: an empty job list, or a job that never progresses.
Both launchers now default to `<repo>\var`, both honour an explicit
`BINARYREPAIR_DATA_DIR`, and both resolve it to an absolute path before use.
`docs/controller-integration.md` shows the aligned commands.
`tests/test_launch_config.py` fails if the launchers drift apart again.

## Limitations and remaining gaps

1. **`route_a` host adapter is not implemented.** The driver refuses it
   explicitly (exit 4) instead of reusing Route B evidence or synthesising gates.
   Route A needs its own measured bundle format before an adapter is honest.
2. **No sidecar.** The attempt `execution` status still cannot be derived from a
   producer sidecar; record 85 and the prototype remain absent from every ref.
   Nothing in this change depends on them.
3. **The real-subprocess test is POSIX-only** (skipped on Windows), so the nine
   variables are verified here through a monkeypatched `subprocess.run`. The
   environment contents, not the process launch, are what that test proves.
4. **No gate status changes.** This is host plumbing: no V-gate, Gate 4/5/6,
   fixture, or acceptance-engine behavior is affected.
