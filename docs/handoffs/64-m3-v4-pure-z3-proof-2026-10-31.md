## 背景与动机

Lead 对 v12 的收件核验明确指出旧 V4 证据的缺陷：

1. valid/free 输入是 concrete bytes，`sat=0/unsat=0/unknown=0/eval=1`，不是符号探索；
2. 没有第二个 deliberately defective candidate 做负校准；
3. hooks/guard 路径未在 hooked strcpy 之外证明；
4. 要求 "实际产生 solver 查询 + solver 记账"。

我进一步实测确认了根因：angr 10.0.4 的 rustylib 后端分支求解在 rust 层完成，Python 层 `is_true`/`is_false`/`satisfiable` 全部 read-only，**无法拿到精确 sat 计数**（已在之前会话如实报告）。

## 本轮的解决方式

按 Lead 给定的方向 1，**放弃 angr 符号执行引擎，改用纯 z3 直接建模**：

- `v4_model.py` 用字节级符号数组 `data : Int -> BV8` + 符号长度 `L`，约束 `data[L]==0 ∧ (∀i<L, data[i]≠0)`，这是真正的符号输入；
- 明确 valid domain（strlen 0..49）与 over-long domain（strlen 50..64，bound=64）；
- forbidden write 判定：dest 写入索引 ≥ 50 即 violation，等价于 `strlen ≥ 50`；
- 直接驱动 z3，每个 `check()` 的 sat/unsat/unknown/query 数/时间都是**精确值**。

## 结果（四候选，全部校准通过）

| 候选 | verdict | 意义 |

| original | **sat** | counterexample strlen=64，缺陷确认 |

solver 记账精确：每候选 1 次 check，original/defective sat=1，routea/routeb unsat=1。

## 诚实局限

这是**函数级、有界符号证明**，非 whole-program 证明：
1. 输入域有界（strlen ∈ [0,64]），非任意长度；
2. `strcpy` 用语义建模（写 strlen+1 字节），未逐字节执行真实 libc；
3. guard 阈值来自反汇编（`>49` / `>=50`），已冻结 hash 供 M4 独立复核；
4. 不是 angr 的 CFG 符号执行（本环境无法拿到精确 sat 计数）。
