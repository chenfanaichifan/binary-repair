## 1. `contract.json`

The contract was rewritten, not patched. Before and after, key by key:

| Key | v2 file | v3 file |
|---|---|---|
| `schema_version` | `2` | **`3`** |
| `input_mode` | `none` (rejected by the v2 model) | `"none"` |
| `invalid_input_response` | absent | absent |
| `invalid_exit_code` | `0` | **deleted** |
| `invalid_stdout` / `invalid_stderr` | absent | absent |
| `max_valid_input_bytes` | absent | absent |
| `target_entry`, `target_signature`, `valid_domain`, `valid_behavior`, `forbidden_behavior` | present | unchanged |
| `dest_capacity_bytes` (100), `capacity_includes_terminator` (true) | present | unchanged |
| `allowed_calls`, `authorized_edits`, `environment_assumptions` | present | unchanged |
| `required_obligations` | six kinds | unchanged (six; `symbolic` not quietly dropped) |

**Why not "v2 plus `input_mode`".** Measured against the checked-out model, not
argued:

```
SecurityContract.from_dict({... schema_version: 2, input_mode: "none" ...})
  ValueError: unknown contract fields: ['input_mode']

SecurityContract.from_dict({... schema_version: 3, input_mode: "none",
                            invalid_exit_code: 0 ...})
  ValueError: unknown contract fields: ['invalid_exit_code']
```

The second line is why `invalid_exit_code: 0` could not stay. In v3 the field set
for `input_mode: "none"` is `_REQUIRED_KEYS_V3_NONE`; anything outside it is an
unknown field, and `0` is a sentinel value for a rejection path this sample does
not have. Deleting it is the same statement the record 106 decision made in
prose: absence is the semantic.

What loads now:

```
SecurityContract.from_dict(contract.json)
  LOADS schema=3 input_mode=none
  invalid_* all None: True
  to_dict() == the file: True        # nothing is re-added on the way out
  contract_sha256: c1684f15bb1c67cb9b3d6752e4023ca670a432ceb92342f6d10d040ee17b4f7c
```

The round-trip equality is the part worth checking: a model that accepted the
shape but re-emitted `invalid_stderr: ""` would put four fabricated fields back
into every serialized contract.

## 2. `defect.json`

Two fields were missing for the intake to read it at all:

```
+ "mechanism": "lifetime"
+ "baseline_mechanism": "bounds-check"
```

`mechanism` is the axis T8.3 differs on (`lifetime` vs the baseline's
`bounds-check`); the intake fails with `defect_mechanism_missing` without it and
with `not_a_distinct_class` if the two match. `trigger_case` stays `null`: the
no-input shape permits it to be absent or null, and it must not name a case that
does not exist.

## 3. Two names for one source — `src.c`

`tools/fixture_intake.py` hardcodes `src.c` in `REQUIRED_FILES` and returns at
`missing_file` before it reads anything else. This sample's source is
`original.c`: that is the name on the gcc line in `build.sh` and
`build.json#argv`, `-g` wrote it into the committed ELF, and
`defect.json#source.path` points at the upstream file that produced it.

Renaming would break the fixture in a way that is easy to miss: `-g` records the
spelling from the command line, so `src.c` produces a different `.debug_str` and
therefore a different digest — the committed `original.elf` (`c9c2632e…23c9`)
would no longer be reproducible from the recipe that ships beside it. Rebuilding
under the new name would fork a second hash for one sample, which records 118
and 119 both refuse.

So `src.c` was added as a **byte-identical alias**:

```
fa84a6bb9df36a8a1ab4d33a7064746d9037247f7599d3cd39659478d4b7f42e  original.c
fa84a6bb9df36a8a1ab4d33a7064746d9037247f7599d3cd39659478d4b7f42e  src.c
```

No upstream byte changed, the recipe still compiles `original.c`, and
`tests/SHA256SUMS` lists both names against the same digest, so an edit to
either one fails the manifest instead of drifting. `PROVENANCE.md` says in the
fixture itself that `src.c` is an alias the build never reads. If M1 makes the
intake take the source name from `build.json#argv`, delete `src.c` and its sums
line; nothing else moves.

This is a compatibility shim, and it is reversible on purpose.

## 6. Gates

- **V3.** No candidate exists, so V3 is `not_run`. When one is produced, the
  behaviour set is **one** no-input case and the ceiling is `1/1`. There is no
  argv, no stdin and no file input, so writing four valid cases would mean
  inventing inputs for a program that reads none.
- **V4.** `not_run`. There is no input domain to reason over symbolically. It is
  not "binary-level" coverage and is not reported as anything.
- **A consequence worth stating now:** `required_obligations` still contains
  `symbolic`. Under this contract any future candidate will therefore be judged
  `inconclusive` on `REQUIRED_CHECK_NOT_RUN`, because V4 cannot run. That is the
  honest verdict under the current obligation set, not a bug in the fixture, and
  dropping `symbolic` from the contract to make it disappear is the contract
  owner's call, not mine.
- **T8.3.** Still blocked. This is the same defect class as the CWE121 baseline
  in mechanism terms (`lifetime` vs `bounds-check` differs, but it is one sample
  and one class), and no second class was invented.

## 7. Open, and deliberately not closed here

1. **The retired synthetic directory.** Its existence is what makes the plain
   intake run fail. Retiring it (and updating `docs/fixtures.md#current-state`
   with it) is M1's edit.
2. **`src.c`.** Remove it once the intake reads the source name from
   `build.json#argv`; until then it is the only way this fixture passes a
   hardcoded layout check without forking the ELF hash.
3. **The valid bytes.** `valid_behavior` and `tests/valid.json` say 99 `A` bytes
   plus one `LF` (100 bytes). That is what `memset(data,'A',99)` +
   `data[99]='\0'` + `printLine` produces, but record 106 leaves the exact
   accepted bytes to the contract owner. If the owner freezes different bytes,
   both files change together.
