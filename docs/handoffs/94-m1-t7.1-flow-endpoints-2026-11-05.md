### `snapshot.agent`

```json
{
  "current_step": "contract",
  "label": "Review the repair contract",
  "source": "controller-derived",
  "steps": [
    {"id": "intake", "label": "Describe the defect", "state": "done"},
    {"id": "contract", "label": "Review the repair contract", "state": "active"},
    {"id": "screening", "label": "Screen the original", "state": "pending"},
    {"id": "repair", "label": "Repair and verify", "state": "pending"},
    {"id": "verification", "label": "Collect evidence", "state": "pending"},
    {"id": "done", "label": "Finished", "state": "pending"}
  ]
}
```

Derivation (persisted facts only, no guesses):

| Fact | `current_step` |
|---|---|
| job `cancelled` | `done` |
| run exists, `phase` not terminal | `repair` |
| run `finished` / `cancelled` | `done` |
| job `finished` | `done` |
| screening `requested`, no run | `screening` |
| job `draft` | `intake` |
| job `awaiting_review` (contract approved) | `contract` |
| job `queued`/`running` without a run row | `repair` |
| anything else | `unknown` |

`unknown` is deliberate: a phase this build does not model must not be rendered as
progress.

### `snapshot.execution`

**Deviation from record 87.** Record 87 lists "`execution` status from sidecar"
(T6.3) and `execution.status` (T7.1). The execution-bridge sidecar belongs to
record 85, which does not exist in any ref, and
`docs/interfaces/execution-bridge-v1.md` defines inbox envelopes but no sidecar
status vocabulary. Rather than invent a producer contract that M2's timeline and
M3's writer would have to match, the status is derived from persisted run rows and
labelled as such:

```json
{
  "status": "queued",
  "source": "controller-derived",
  "sidecar": null,
  "note": "Derived from persisted run rows; no producer sidecar exists in this build.",
  "run_id": "...", "phase": "queued", "outcome": null,
  "started_at": "...", "finished_at": null
}
```

`status` values: `not_started`, `queued`, `running`, `completed`, `failed`,
`cancelled`, `unknown`. `finished` maps to `failed` only for the explicit
`rejected`/`error`/`failed` outcomes; nothing upgrades an unknown run phase.

**Shape change:** `execution` was a string (`"queued"`, `"draft"`) and is now an
object, because record 87 asks for `execution.status`. The old value is preserved
verbatim as `execution_phase` so an older reader loses no information. The only
in-tree consumer was `tests/integration/test_controller_api.py`, updated with the
new assertions. No GUI file reads this field.

### `GET /api/jobs/{id}/analysis`

```json
{
  "job_id": "...", "purpose": "screening", "phase": "awaiting_review",
  "status": "not_provided | requested | available",
  "requested_at": null,
  "detail": "no screening has been requested for this job",
  "screening": null,
  "artifacts": []
}
```

- `available` requires registered `analysis_*` artifacts (written by M5's ingest,
  produced by M3's executor). The controller never creates them.
- `screening` stays `null` until a producer-side summary artifact is defined; the
  controller does not synthesise one from the artifact list.
- Artifact entries use the T6.3 metadata shape, so `available` per artifact and the
  download URLs behave like every other artifact.

### `POST /api/jobs/{id}/analysis`

- `202` — request recorded (`status: requested`, server timestamp).
- `200` — already requested or already available (idempotent; `requested_at` does
  not change).
- `409` — contract not approved, job cancelled, or a repair run already exists.
- `404` — unknown job.

This build has no screening executor, so a request produces no evidence. That is
the honest state: `requested` is not a result, and `GET` does not move to
`available` until real artifacts arrive. No worker row, run, or attempt is created
by this endpoint, so the acceptance path is untouched.

### `GET /api/jobs/{id}/comparison`

Rendered only from a registered `behavior_comparison` artifact:

```json
{"job_id": "...", "status": "not_provided", "detail": "...", "comparison": null, "artifacts": []}
```

When an artifact exists: `status: available`, `artifacts` carries its metadata, and
`comparison` is the parsed JSON. Non-JSON, missing bytes, or files over 2 MiB keep
`status: available` (the artifact is real) but set `comparison: null` and explain
why in `detail` — a malformed producer artifact is reported, not hidden and not
turned into a failure verdict.

## Limitations

1. **No screening executor.** `POST /analysis` records intent; nothing runs. M3's
   T6.2 executor and M5's T7.2 ingest are the writers that will make `available`
   appear.
2. **No sidecar.** `execution.sidecar` stays `null` until record 85 exists. The
   derived status is bookkeeping over run rows, not producer evidence; M4 should treat
   `source: controller-derived` as the boundary marker.
3. **`screening` summary is unmodelled.** No producer artifact contract exists for
   it yet, so the field is `null` by design.
4. **No gate or verdict change.** This adds read endpoints and derived display
   fields; `app/domain/acceptance.py` is untouched.
