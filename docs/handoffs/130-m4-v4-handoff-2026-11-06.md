## 1. What was asked, and what makes it runnable

The ask had four parts, and the fourth is the one that changes the design: after
the package, the address, and the account, **`sh run_selfcheck.sh` has to exit 0
for real, from a clean directory.**

That is not a formality. The previous draft of the check ended with

```sh
"$PY" "$HERE/scripts/selfcheck.py"
echo "exit=$?"
```

which prints the interpreter's status and then exits 0 regardless — a script that
cannot fail. The version in this package runs the check, keeps `rc`, refuses to
continue when it is non-zero, compares the normalised result against the recorded
one, and exits with the comparison's status. It was then run in an empty
directory as `m4verify` and returned 0, and the transcript is in the evidence
(`02-clean-run.txt`).

Path resolution changed for the same reason: everything is derived from the
script's own location, so the package can be extracted anywhere and invoked from
any working directory. The old copy hardcoded `/home/lab/...`, which would have
failed the moment it ran under a different account.

```
  scripts/summarize_output.py        one-screen summary of an output file
  inputs/v4_harness.py               the producer, byte-identical to record 128
  inputs/candidate.elf               repaired binary     46d16e99…
  inputs/original.elf                negative control    c9c2632e…
  inputs/contract.json               v3 no-input        8a2b408c…
  expected/selfcheck.expected.json   normalised 18-check result
  expected/harness-output.expected.json   the producer's output  9c6eeda7…
  SHA256SUMS                         12 rows, all files above
```

The inputs are copies, not references: the package must run for someone who has
nothing but the package. Their digests are checked by the self-check, so a
tampered input fails the run rather than quietly changing the answer.

`expected/selfcheck.expected.json` holds per-check `ok` flags, the engine block
and the pass count; machine-specific text (hostname, platform, interpreter path)
is printed but deliberately kept out of the comparison, so the file is portable
while the checks stay strict. `expected/harness-output.expected.json` is compared
with `cmp`, whole file, because a producer whose numbers drift by one field is
exactly what this is meant to catch.

## 5. Why the evidence sits outside the package

A transcript of checking a tree cannot contain the hash of the sums that cover
it — the file would have to state its own digest. So `SHA256SUMS` inside the
package stays a plain list of the 12 files, and the transcripts live here, hashed
separately (`54fe158d…78fb`).

## 6. Limits, stated where a reader will hit them

- **The address is a DHCP lease**, not a static configuration. It is bound to the
  VM MAC and has been `192.168.30.128` in every window recorded since 2026-10-22,
  but a reboot could in principle move it. The README gives
  `vmrun getGuestIPAddress` as the way to ask rather than guess. Making it static
  would mean editing the guest's netplan and risking the only path into the VM;
  a discoverable address is the cheaper trade.
- **The producer's docstring is stale.** `inputs/v4_harness.py` still says the
  output "is written only through `write_v4_evidence`", which stopped being true
  in record 128 when the second writer was deleted and M1's adapter took over.
  The code writes the measurement file directly. The sentence is left in place
  because the file's sha256 is what records 128 and 129 vouch for; the README says
  which part to trust.
- **No gate.** V4 stays `not_run` in the 124 bundle. Running these scripts says the
  environment and the producer are reproducible; it says nothing about whether the
  evidence suffices.
- **No `verified_by`.** Nothing in the package, the record or the evidence sets it.
  The producer writing the verifier's field would be the same error as self-issuing
  a pass.
- **One sample.** CWE416 no-input only. T8.3 stays blocked; no second defect class
  exists here and none is implied.
