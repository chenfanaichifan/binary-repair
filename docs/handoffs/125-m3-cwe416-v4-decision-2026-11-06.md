## 1. Three structural reasons a quick V4 is wrong here, not just lazy

The instruction was "either a harness with solver accounting, or keep
`not_run`". Keeping `not_run` is not a deferral of work that someone else will
magically do — it is what the code already expects. Three places say so:

**Scope.** `app/domain/scopes.py` maps `symbolic → model` and says it outright:
"`V4 symbolic` is `model` even when it passes, which is exactly why a passing V4
alone cannot be read as machine-level proof." So "binary-level V4" is not a
result I could produce carefully or carelessly — it names a category the scope
table does not have.

**Writer.** `routeb/attempt_writer.py` sets `"V4": "not_run"` with the detail
"symbolic check not run", unconditionally. There is no bundle field through
which a V4 result travels. If I ran a harness by hand today, the number would be
a file in a directory; the attempt built from that bundle would still say
`not_run`. Making it say otherwise is a Route B change, not an evidence change —
and it is not M3's file.

**Acceptance.** `acceptance.py#_non_success_verdict` maps a required `NOT_RUN`
obligation to `INCONCLUSIVE` / `REQUIRED_CHECK_NOT_RUN`. So the current bundle is
already handled correctly: it is inconclusive, not secretly a pass, and there is
nothing to "rescue" by inventing a V4.

## 2. What killed the earlier V4 submissions

Four rejection reasons, from records 63, 64, 66, 67. A new harness has to answer
each one by name, not in general:

| Rejection | What it looked like | Countermeasure a real harness needs |
|---|---|---|
| Concrete inputs | "symbolic" run whose inputs were `'A'` bytes; `eval=1`, `sat=0`, `unsat=0` | symbolise the argued-over values; a run with zero solver queries is a replay, not a model |
| Silent `max_steps` | exploration stopped at the step cap and reported "proven" | step cap exceeded → `unknown`, never `proven`; report steps and cap |
| No accounting | counts missing, so a vacuous run and a proof look alike | per-run `sat/unsat/unknown/eval/steps/max_steps`, asserted against the bound |
| Entry mismatch | script explored `0x4012B0` while the record named `0x4018ec` | resolve `contract.json#target_entry` in the ELF and assert the explored address equals it |

## 3. Definition of done, if someone builds it

Written as a checklist so it can be refused point by point rather than argued
about in prose:

1. `target_entry` resolved from the contract, matched against the ELF symbol
   table, and printed next to the address actually explored.
2. The argued-over state is symbolic, and the run reports at least
   `sat`, `unsat`, `unknown`, `eval`, `steps`, `max_steps` per query.
3. `steps >= max_steps` is reported as `unknown`. No path may print "proven"
   after the cap was hit.
4. A stated bound with a reason, not a number that happens to terminate.
5. A **negative control**: the same harness on `original.elf` must **not** prove
   the repaired property. Without it the property is vacuous and the pass is
   meaningless — this is the same argument as the V3 control flipping `1/1` to
   `0/1`.
6. Engine and versions recorded (`angr 10.0.4.post1`, `z3 5.1.0` are installed in
   `/opt/angr-venv` on the guest), plus the harness hash.
7. Scope written as `model`, `claimed_scope` filled with what the bound covers.
8. A writer path so the result can actually be recorded — otherwise item 1–7
   produce a file nobody consumes.

Items 1–7 are guest work. Item 8 is not, and without it a harness changes
nothing about the outcome. That split is the reason this pass stops at
`not_run` instead of shipping a harness that cannot land.
