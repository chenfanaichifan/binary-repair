# How the guest was reached

At the start of this window the usual path was down:

$ ping -n 2 192.168.30.128
  Request timed out.  Request timed out.
  Packets: Sent = 2, Received = 0, Lost = 2 (100% loss)

$ ipconfig  (VMware Network Adapter VMnet8)
  Autoconfiguration IPv4 Address. . : 169.254.29.225

Get-Service "VMware NAT Service" answered Stopped, so VMnet8 had no address in
192.168.30.0/24 and there was no IPv4 route to the guest. The virtual switch
itself was up — ARP still resolved the peer:

$ arp -a  (interface 0x5 = VMnet8)
  192.168.30.128       00-0c-29-94-c6-0f    dynamic

00-0c-29-94-c6-0f is the VM's ethernet0.generatedAddress, so only routing was
missing. The guest was therefore reached over IPv6 link-local, whose address
follows from that MAC by EUI-64:

  00:0c:29:94:c6:0f  ->  fe80::20c:29ff:fe94:c60f  ->  ssh lab@fe80::20c:29ff:fe94:c60f%5

$ ssh -i .tmp/ssh/id_ed25519 lab@fe80::20c:29ff:fe94:c60f%5 "id -u; hostname; uname -sr"
  uid=1000
  binrepair-vm
  Linux 6.8.0-147-generic

Partway through the window the NAT service came back on its own: VMnet8 then
had 192.168.30.1 and the host could ping the guest again. The guest could not
use it, though, and still cannot:

$ ipconfig | grep -A6 VMnet8 | grep IPv4        # on the host
  192.168.30.1
$ ping -n 2 192.168.30.128                      # on the host
  Packets: Sent = 2, Received = 2, Lost = 0 (0% loss)

$ ping -c1 -W2 192.168.30.1                     # on the guest
  (no reply)
$ ip -4 addr show | grep inet                   # on the guest
  127.0.0.1/8 scope host lo
  192.168.30.128/24 metric 100 brd 192.168.30.255 scope global dynamic enp0s18
$ curl -sI https://pypi.org/simple/             # on the guest
  (no output)

So the guest has an on-link address and nothing else: no gateway, no egress.

# What that rules out

provision_angr_venv.sh installs 54 distributions from PyPI, so it cannot run in
this window — there is no egress to run it against. It is shipped as a recipe,
not as something executed here, and the README says so instead of implying a
rebuild happened.

What did run is its verification half, against the interpreter the V4 evidence
actually used: selfcheck.py (18 checks) and the end-to-end rerun that came out
byte-identical to the committed harness-output.json. Neither result depends on
how the guest was reached.
