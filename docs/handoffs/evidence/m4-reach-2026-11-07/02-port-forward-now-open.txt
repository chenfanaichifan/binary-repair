## three paths, measured — not inferred from the rule existing

$ ssh -p 2222 lab@127.0.0.1                 # loopback
  logged in as lab on binrepair-vm

$ ssh -p 2222 lab@10.11.0.132                 # the WLAN address a remote client uses
  logged in as lab on binrepair-vm

$ ssh -p 2222 lab@192.168.30.1              # from inside the guest, back through the host
lab@192.168.30.1: Permission denied (publickey).
  Not a timeout, which is the part that matters: the TCP path and the forward
  both work and sshd answered. What fails is authentication, because the guest
  holds no private key of its own — the key that logs in as lab lives on the
  host at .tmp/ssh/id_ed25519 and never goes into the guest.

$ ssh -p 2222 lab@10.11.0.132  as m4verify, with the lab key   # must be refused
  m4verify@10.11.0.132: Permission denied (publickey).
  Refused, which is the point: the forward carries the connection, sshd still
  decides the identity. An open port is not an open account.

## two limits of this route, recorded now rather than discovered later

  1. The host address is DHCP and it has already moved once. It was
     192.168.43.11 when yesterday's record was written; the Wi-Fi changed and
     it is 10.11.0.132 now. Quote the command, not the number:
       Get-NetIPAddress -AddressFamily IPv4 | ? InterfaceAlias -eq WLAN

  2. That address is private (a /20). A client can use this route only if it
     can route to that network — the same Wi-Fi, or a VPN into it. A machine
     on the open internet cannot, and no rule on this host changes that.
