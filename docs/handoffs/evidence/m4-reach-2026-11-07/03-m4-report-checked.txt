## 1. the key does not match the one that is installed

  M4 reports its local private key has fingerprint
    SHA256:FZfxZXkW…DQQ
  while the key installed on m4verify is
    SHA256:bRq28b6J…84Q

  Both statements are true and they contradict each other in the only way
  that matters: a signature made with the first will not verify against the
  second, so M4 cannot log in even with the route open.

$ cat ../m4-key-install-2026-11-06/m4_guest_key.pub   # installed 2026-11-06, from the text in that request
  ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBFmDHmwn/0KeulZ32w97zmV2jP+p7kGMdWew2rZnbdq m4-guest-replay-2026-11-06

$ ssh-keygen -lf ../m4-key-install-2026-11-06/m4_guest_key.pub
  256 SHA256:bRq28b6JG3LXILy3iayXdW/HdSre8mCofnd6B+8L84Q m4-guest-replay-2026-11-06 (ED25519)

  The public half of the installed key was supplied as text; its private half
  was never on this host. The key M4 actually holds is a different keypair.
  Until one of the two is resolved, access fails at authentication and looks
  exactly like a routing problem — which is why this is worth fixing before
  another window is spent on the network.

  Resolution, either way, is one command on M4 side:
    ssh-keygen -y -f <the private key M4 will use>   # prints the public half
  If M4 intends to use FZfxZXkW…, that public line gets installed and the
  bRq28b6J… line is retired. If M4 holds the private half of bRq28b6J…, then
  nothing needs installing and the two files just need to be told apart.
