## 2. Changes

`app/controller_api.py`

- **Job-scoped artifact routes.**
  `GET /api/jobs/{job_id}/artifacts/{artifact_id}` and
  `GET /api/jobs/{job_id}/artifacts/{artifact_id}/download`.
  An artifact id belonging to another job returns `404`, the same answer as an
  unknown id, so job membership cannot be probed.
- **Byte verification before serving.** Download rehashes the file and compares
  it with the registered `sha256` and `size_bytes`. A mismatch is `409` and the
  bytes are never sent. Metadata uses the same check and reports
  `available: false` with an `unavailable_reason` instead of a bare path test.
- **Listing integrity is explicit.** The list only compares file size (cheap);
  each row now carries `integrity: "size"` or `"sha256"` so a consumer can tell
  how far the check went.
- **No fabricated artifacts.** The previous fallback invented an entry with
  `id: ""`, `role: "original binary"` and `available: false` for a job with no
  artifact rows. That placeholder is gone; such a job now returns
  `{"A": [], "B": []}`. Job creation already registers the real `original`
  artifact row, so nothing was lost.
- **Visuals are artifact-backed.** `/api/jobs/{id}/visuals` returns
  `available: true` only when the job has an artifact whose role is one of
  `analysis_expected_effects`, `analysis_assumptions`, `analysis_uncertainties`,
  `analysis_v3`, `behavior_comparison` (the vocabulary from
  `docs/interfaces/artifact-roles-v1.md`). It then lists those artifacts with
  job-scoped download links. Otherwise it returns `available: false`,
  `synthetic: false` and a reason. The synthetic demo disassembly in
  `app/visuals.py` is no longer reachable through the controller API.
- Legacy `/api/artifacts/{id}` and `/api/artifacts/{id}/download` keep working
  and now apply the same verification.

`tests/integration/test_controller_api.py` gains six tests: verified job-scoped
download, cross-job 404 for both metadata and download, size tamper, same-size
`sha256` tamper, no-placeholder listing, and the visuals contract.

## 4. Blocked: `execution` status from sidecar

Record 87 expects the controller to derive an `execution` status from a sidecar.
No sidecar contract exists that M1 can implement against:

- record 85, which record 87 cites as the definition, is absent from every ref;
- the bridge protocol that does exist
  (`docs/interfaces/execution-bridge-v1.md`, on `member-5/complete-m5`) defines
  the inbox envelope, the bundle directory and the reject list; it does not
  define an execution sidecar or its status vocabulary.

M1 did not invent a shape, because M2's timeline (T7.6) and M3's bundle writer
would both have to match it. The attempt rows already persisted in SQLite carry
`phase`, `outcome`, `reason` and `failing_obligation`; exposing those would be a
real status, but calling it "from sidecar" would misdescribe where it comes
from. This needs record 85 or an explicit decision to serve attempt-derived
status under a different name.
