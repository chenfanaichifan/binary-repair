# Two AI binary repair paths — scripted acceptance evidence

Generated by `scripts/capture_ai_binary_repair.py` (2026-11-13).  The model is a
deterministic **scripted** client: no network/provider is used.

## Path 1 — `asm_roundtrip`

The target ELF function is disassembled to assembly text; the model returns
replacement assembly; clang assembles it to a machine-code block that is injected
and function-entry redirected; the deterministic gate verifies the candidate.
Positive evidence: ELF i386, ELF x86-64 and ELF arm64.

## Path 2 — `binary_direct`

The model emits raw machine-code guard bytes (injected and call-redirected) or
same-length in-place edits; a strict validator constrains the bytes and the
deterministic gate verifies.  Positive evidence: PE x86-64, PE arm64, ELF i386,
ELF x86-64, ELF arm64, ELF i386 memcpy; on macOS additionally Mach-O x86-64 and
Mach-O arm64 via the **native** runtime gate.

`negative-bytes-noop-guard.json` shows a structurally valid but semantically
empty guard (`c3` = `ret`) rejected by the deterministic runtime gate
(`verified=false`, `rejected`).

**No AI increment is measured.**  The scripted model is a stand-in; direct-path
candidates coincide with the v5 deterministic baseline, and assembly-path
candidates differ in representation but do not prove extra coverage.  A
real-provider, gate-blind/PoC increment experiment remains future work.
